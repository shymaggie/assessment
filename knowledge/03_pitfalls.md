# 复测误判经验与工程取舍

> 以下每条都对应代码或配置里的具体位置，都来自实际调试过程。

## P-01 响应长度抖动的来源与对策

**误判场景**：把两次请求的长度差当成漏洞证据，实际来源是：动态响应头（Date 每秒变）、Set-Cookie 会话轮换、页面内嵌时间戳/随机 nonce。

**对策（已实现）**：vulnlab 靶场响应体逐字节确定（无时间戳/随机数）；判定只比对 body_length / body_sha256，动态头按 R-STRIP-01 剥离；比例阈值 0.5（R-T1-01）远高于任何残留抖动幅度。

## P-02 WAF 拦截 ≠ 漏洞修复

**误判场景**：复测发现 `<script>` 被拦 → 报告「已修复」。真实世界：编码变体（`%3Cimg onerror=...`）、大小写混淆、标签替换均可绕过关键字拦截。

**对策（已实现）**：R-T2-01 用双探针——字面量探针测「拦截是否存在」，变体探针测「漏洞本体是否仍可触达」。变体仍原样反射给 SURFACE_PATCH；两条都被拦只给 WAF_FULL_BLOCK（拦截面完整 ≠ 代码修复）；只有两条都以「编码串出现」的形式回显（输出编码的正向证据）才给 PATCHED（v2 修订，见 P-23）。这正是本靶场 T2 的设计原型，也是「区分实际修复与表层变更」复测目标的直接实现。

## P-03 为什么用 SHA-256 + 归一化比对，而不是子串匹配

子串匹配（如找 "Forbidden" 字样）会误伤：不同修复实现返回不同文案但语义相同（都是统一拒绝）。SHA-256 比对回答的是更严格的问题——「两条路径是否逐字节走了同一个拒绝逻辑」，这是统一中间件修复的架构特征。代价是过严（文案重构会被误判 VULNERABLE），在 R-ERR-01 的 INCONCLUSIVE 兜底下，过严的误判可被人工复核纠正，漏判则不可逆——两害取其轻。

## P-04 网关无 Divide：比例为何本地算

差值经 calculator Subtract 过网关留审计；但 OctoBus calculator 只暴露 Add/Subtract。若为除法再写一个能力包，等于为纯算术增加一次网络依赖与故障面。取舍：**输入（差值）已被审计，除法是确定性纯函数，本地计算不损失证据链**——分工边界写进 rules.json `ratio_rule.why`，由 pipeline 加载（缺失键 Fatal）。

## P-05 探测失败 ≠ 修复成功

**误判场景**：接口超时/403 了 → 报告「已修复」。可能只是：服务挂了、网关白名单没配、WAF 把复测 IP 封了。

**对策（已实现）**：探针传输层失败一律 INCONCLUSIVE（R-ERR-01），报告显式列出 transport_errors 供人工复核，绝不把「探不出去」计为「已修复」。

## P-06 复测必须可复现：固定靶、固定判据、固定矩阵

复测与渗透测试不同：目标是**对同一历史漏洞给出随时间可对比的结论**。因此探针矩阵固定在代码里（probe_matrix）、判据版本化在 rules.json（report 记录 rules_version）、靶场响应确定性——任何一次重跑得到的差异都来自「目标状态变化」，而不是「工具随机性」。

## P-07 受控靶场的「自证」边界（诚实声明）

本靶场的 WAF 拦截特征串（`WAF-BLOCK`）与判据（rules.json `t2.block_marker`）同源——判定器对**这个靶场**完全确定，但对真实 WAF 的拦截页**不具泛化性**（各家 WAF 拦截页指纹不同）。这是受控复测靶场的固有边界：要泛化到真实目标，需把特征串换成可配置的指纹规则集（rules.json 扩展为 per-target fingerprints）。本考核场景内这是合理取舍，但应在报告边界声明中主动说明。同理，T1 的「探针打偏防护」（R-T1-02，无标记请求返回 400）也是靶场侧配合实现——真实目标的等价防护需判定器先做基线探针校验。

## P-08 权限报错的误诊链：先验假设取代了读源码

**误判场景**：`instance start` 报 `fork/exec …/bin/probe.js: permission denied`。三连假说排查（源文件读权限→目标目录属主→整卷 chown）全部无效，因为三个动作都在补「读」权限，而报错来自**执行位缺失**——OctoBus supervisor 直接 `exec.Command(入口 JS)`，shebang 脚本必须有 x 位（官方 supervisor_test「not executable」→同款报错）。更隐蔽的是首次修复用 `chmod -R a+rX`：大写 X 语义是「仅对已有 x 位的文件/目录补位」，对 644 的 probe.js 永远空转，制造了「修了没用」的假象，把排查拖成三轮。

**对策（已实现）**：入口脚本 `chmod 755`（本地包已同步 755，重导入不复发）；排障纪律——报错文案里的动词（exec/copy/open）先于假设定位到源码调用点，再对症下药，而不是按「权限问题」直觉轮流撒 chmod。

## P-09 能力声明面 ≠ 运行时实现面：三层对齐才算能力可用

**误判场景**：`capset select-method` 授权 Subtract 成功 → 想当然认为「能调」。实际预置 calculator 包 proto **声明**了 Add+Subtract（service list 可见），但运行时 handler 只注册 Add——每次 Subtract 调用都被实例回 HTTP 400 `unimplemented: The server does not implement the method Subtract`（网关审计 404 NotFound）。授权通过只证明「声明面 ∩ 授权面」非空，「实现面」是独立第三层。

**对策（已实现）**：能力上线前做**三层对齐核验**——① `service list` 看声明面；② grep 运行时 handler 注册键看实现面；③ 实弹重放（curl 带回显）看端到端。修复走同 id upsert（importer.go UpsertService）+ `instance restart`，实例 id、capset 授权、调用方代码零改动。延伸视角：这是「接口契约与实现漂移」的供应链缩影——SDK/服务包声明的方法面与实际实现脱节，与业界 SDK 治理「声明 vs 实测」方法论同构。

## P-10 验证必须分层：文件层绿 ≠ 端到端通（附防御式兼容写法）

**误判场景**：热替换 calculator handler 时，用 `grep -c "CalculatorService/"` 输出 2（Add+Subtract 键都在文件里）判定「修复成功」——随后 `instance restart` 报 `health check failed: connection refused`，实例根本起不来。同一修复链上还连环踩了三个分层陷阱：① 官方示例包是 SDK 模式（require `@chaitin-ai/octobus-sdk`），旧 runtime 是裸 gRPC 模式且无该依赖——「字符串在文件里」≠「依赖可解析」，require 首行即崩；② 跨环境重建文件时丢失首行 shebang（hardening.go 注释原文 "Runtime entries are shebang scripts"，supervisor 直接 `exec.Command(entry)` 无 node 兜底）——755 + 无 shebang = 内核 ENOEXEC「exec format error」；③ `node --check` 对 `.patched` 扩展名报 ERR_UNKNOWN_FILE_EXTENSION——语法检查对象必须是落位后的目标文件名。

**对策（已实现）**：① **四层验证链**——文件层（grep 键存在）→ 语法层（`node --check` 对落位后的 .js）→ 进程层（`instance restart` 的 health check + `tail stderr.log`，supervisor.go:286-298 把进程 stderr 落盘到 `DataDir/instances/<id>/stderr.log`）→ 端到端层（curl 实弹带回显），单层绿不算通；② **真实报错优先**——`logs --instance` 返回的是网关审计流水而非进程 stderr，崩溃栈必须读 stderr.log 或前台手动跑入口脚本；③ **防御式兼容**——跨环境替换代码时避免硬编码库的命名空间挂载路径（如 `proto.grpc.calculator.v1`），改「标准路径优先 + 结果树深搜 `.service` 属性兜底」的双通道解析，对 proto-loader/grpc-js 版本行为差异免疫。延伸视角：与「声明的规则未被实际使用」风险同类——「声明的修复未被端到端验证」，单点证据不能替代链路证据。

## P-11 网关接口命名漂移：契约名 ≠ 运行时名

**现象**：同一份代码、同一个能力包，某些轮次探针响应字段是 `body_length`（proto 声明名），另一些轮次变成 `bodyLength`（protojson lowerCamelCase）。判定器直接索引 `body_length` 取不到值，`judge_t1` 在减法前抛 `KeyError`，被 `main()` 兜底捕获。

**现场证据**：`evidence/20260930110008-139/`——该轮 6 次 ProbeHttp 全部成功（status 200/403），但 `octobus_calls_log` 仅 6 行、**无 Subtract**，报告为 INCONCLUSIVE；原因即本坑。

**定位方法**：不看报告看证据链——`calls` 数与探针数不符（6 vs 7）即说明判定在减法前就断了；再把该轮 evidence 的键名与 proto 声明逐一对齐。

**处置**：`normalize_probe()` 做 camel→snake 的防御式别名（只重排键名，不改数值），判定器只认 proto 声明的 snake_case。**证据文件仍保存网关原样响应**（不人为改写，便于审计对账），归一发生在判定读取时（见 README 第 7 节）。

**判定意义**：该轮失败方向是保守的（报 INCONCLUSIVE 而非误判 PATCHED），与 R-T1-02「探针打偏不得伪装成已修复」同一防线。**推论：任何接口适配层的失败都必须落到 INCONCLUSIVE，绝不能落到 PATCHED。**

## P-12 长度/字节一致性可作判据的前提，与不可作判据的字段

**前提一：长度与哈希必须取自「完整响应体」，不能取自 excerpt。**
`body_excerpt` 只是完整 body 的前 N 字节展示副本；若用 excerpt 长度做判据，当响应体被截断时会掩盖差异 → 假阴性。
`body_length` 取自 `buf.length`、`body_sha256` 对完整 `buf` 计算，二者共同支撑「逐字节一致」这一强判据。

**前提二：「逐字节一致」不能只看长度。** 等长但内容不同（sha 不同）既不是干净修复、也不构成可用注入，
必须转 INCONCLUSIVE 交人工——单看长度会把「等长的语义替换」误判成 PATCHED。

**不可作为判据的字段及其原因**：

| 字段 | 原因 | 处置 |
|---|---|---|
| `headers` 中的 `Date` / `Set-Cookie` / `Server` / `X-Request-Id` | 每次请求都变，纳入全等比较会把「已修复」误判成「未修复」（假阳性） | R-STRIP-01 剥离后再比 |
| `elapsed_ms` | 网络抖动，与修复状态无因果关系 | 不参与任何判定 |
| `status` 单值 | 靶场对「无注入标记」的请求返回 400，与「已修复的统一 403」不同；只看 status 会把探针打偏当成已修复 | 仅 200/403 进判定（R-T1-02） |
| `body_excerpt` 长度 | 见前提一，截断即失真 | 只用于关键字匹配与展示 |

**失效场景（本靶场已验证）**：若目标响应含时间戳/CSRF token 等动态内容，即便漏洞已修复，`ratio` 也不会归零——
此时只按长度判 PATCHED 必然漏报。故 PATCHED 的判据是「ratio==0 **且** sha256 全等」，两条同时成立才判；
中间灰区一律 INCONCLUSIVE。**失败方向一律偏保守：证据不足不硬判。**

## P-13 proto3 零值在 protojson 下被省略：四个字段的缺失语义各不相同

**现象**：`Subtract(18,18)` 的响应是**空对象** `{}`（没有 `result` 键），而 `Subtract(45,0)` 的正常响应是 `{"result":45}`。对照实测：`call_octobus.py` 中 `return int(r["result"])` 直接抛 `KeyError: 'result'`，被 `main()` 的 try/except 兜成 INCONCLUSIVE —— **T1 判 PATCHED 的那条路径在结构上不可达**。同一根因还命中空响应体：`/status/200`（0 字节）的探针响应键集实测为 `[bodySha256, elapsedMs, headers, status]`，**没有 `bodyLength`，也没有 `error`**。

**根因**：protojson 序列化时省略 proto3 的**默认零值**字段。受影响的共四个：`result`（int32）、`bodyLength`（int32）、`bodyExcerpt`（string）、`error`（string）。**JSON 层无法区分「这是合法的零值」与「这个字段没被设置」**——两者都表现为「键不存在」。

**关键判据——零值可补性**：

| 字段 | 零值 | 零值在业务上是否可能合法出现 | 缺失时的正确解释与处置 |
|---|---|---|---|
| `result` | `0` | **可能**（减法结果本就可能是 0） | 补 `0`，正常判定 |
| `bodyLength` | `0` | **可能**（空响应体，已实测） | 补 `0`，正常判定 |
| `bodyExcerpt` | `""` | **可能**（空响应体） | 补 `""`，正常判定 |
| `error` | `""` | **可能**（无错误即正常态） | 补 `""`，正常判定 |
| `bodySha256` | —— | **不可能**（空响应体的 sha256 也是 `e3b0c442…`，恒非空） | **缺失只能是异常形状 → fail-closed** |

> **判据本身**：一个字段的零值若在业务上「可能合法出现」，则缺失可补默认值；若零值在业务上「不可能出现」，则缺失必然是异常形状，必须 fail-closed。**「补零值」不是一个可以无脑套用的动作**——它只对前四个字段成立。

**反例（把判据用错的后果）**：若按同一逻辑把 `body_sha256` 也补成 `""`，两个**都没有哈希**的探针会因 `"" == ""` 互相判等、`ratio` 归零 → 直接判 **PATCHED**。实测该写法确会产出这个错误结论；本补丁在该分支返回 **INCONCLUSIVE**。这是典型的 **fail-open**：为了「让程序别崩」而补默认值，把「证据不足」补成了「证据显示已修复」。

**处置（已落地）**：
1. `call_octobus.py`：`result` 缺失时——**空对象**（响应体就是 `{}`）解释为 0；**非空但无 `result`** 视为契约破损，抛 `RuntimeError` 而非静默取 0。**区分这两种情况是本坑的第二层**：前者是零值省略，后者是契约破坏，不能用同一套默认值糊过去。
2. `pipeline.py` 的 `normalize_probe()`：对 `status` / `body_length` / `body_excerpt` / `elapsed_ms` / `headers` 补零值缺省；**`body_sha256` 例外**——缺失即置 `error="MALFORMED_PROBE: ..."`，转入 INCONCLUSIVE。
3. 回归用例：**桩打在 `call_method`（HTTP 边界），不打在 `subtract`**。

**测试桩位的教训**：原用例在 `subtract` 上打桩，而缺陷恰恰在 `subtract` 内部——**桩把它自己该被测的那一层整个替换掉了**，于是 38 个用例全绿、缺陷照样活着。移到 HTTP 边界后：未打补丁 **7 failed / 39 passed**，打补丁 **46 passed**（本机 python3.12 与服务器 python3.10.12 结果一致）。上述为当次修复节点的计数快照，非当前用例总数——此后用例有增补，以 `pytest tests/ -q` 实测为准。

**判定意义**：本坑的两种失败方向截然不同——`KeyError` 崩掉是**保守的**（INCONCLUSIVE），而「把缺失的 sha 补成空串」是**激进的**（误判 PATCHED）。**修复必须同时消掉这两头**：既不能崩，也不能为了不崩而放宽判据。与 P-11、R-T1-02 同一条防线。

## P-14 工具返回的成功状态 ≠ 真实生效状态

**总则**：OctoBus 管理面返回体描述的是**落库结果**，不是**运行时状态**。二者之间隔着一次 reload/restart，以及一层看不见的值归一化。**只看返回体——哪怕它把新哈希、新时间戳都给你了——不足以判定生效。**

**已实测的五个实例**：

| # | 操作 | 返回体说 | 实际发生 |
|---|---|---|---|
| 1 | `instance update-config` **不带 `--restart`** | `ConfigSHA256` 变成 `6e992395…`、`UpdatedAt` 更新 | **`PID` 仍是旧值（14），运行时仍报旧 allowlist**——静默失效、无任何警告 |
| 2 | 出口白名单写**裸主机名** | 写入成功 | 运行时被**静默归一**为 `host:80`；`https://` 走 443 → `EGRESS_DENIED: …:443 不在出口白名单内`。「放行主机」实际只等价于放行 80 端口 |
| 3 | 宿主机直连 `octobus` CLI | —— | 报 **`daemon is not running`**。真实原因是 `--addr` 默认 `127.0.0.1:9000` 只在容器内有效；报错把排查引向「daemon 死活」，而它一直活着 |
| 4 | `capset add-token` 用**已存在的 ID** | `400` + 原始 `UNIQUE constraint failed: capset_tokens.capset_id, capset_tokens.id` | 令牌**只能追加、不能覆盖**。叠加「`list-tokens` 把整个列表遮蔽成 `******`」与「`remove-token` 必须提供 ID」，构成**轮换闭环陷阱**：最自然的做法撞约束，想先删又枚举不出来 |
| 5 | `--token-file` 配 `docker exec` | 找不到文件 | CLI 运行在**容器内**，读的是容器内路径；宿主机路径永远不可见 |

**三条共性**：
1. **返回体描述「库的状态」，不描述「进程的状态」。** 写库成功与运行时生效之间隔着一次重载——而重载需要显式请求（`--restart`），省略即静默失效。
2. **你写的值不是运行时看到的值的原样。** 中间存在一层未声明的归一化（裸主机名→`:80`、camelCase→snake_case），且**不告知**。
3. **报错指向的症状与真实原因不一致。** `daemon is not running` 之于 `--addr` 默认值；`UNIQUE constraint failed` 之于「该 ID 已被占用，请换 ID 或先删除」。

**对策：配置类操作一律要求「双向功能反证」。** 改完必须观察到**行为发生预期变化**，还原后必须观察到**行为退回**——只比对返回体的哈希/时间戳不够（实例 1 的返回体是**完全正确**的）。本次白名单还原即按此执行：`ConfigSHA256` 逐字符回归 `94b1ceec…` ✓、`allowedHosts` 回读 ✓、**功能复验重新拿到 `EGRESS_DENIED`** ✓——三轴齐证才敢宣布还原完成。

**与 P-09、P-10 的关系**：P-09「能力声明面 ≠ 运行时实现面」说的是**静态声明**与实现不符；P-10「文件层绿 ≠ 端到端通」说的是**中间表示**与运行不符；P-14 是它们的**操作侧对偶**——**「操作返回成功」与「状态已变更」不符**。三者同源：**任何单点信号都不足以证明系统状态，必须拿到端到端的行为证据。**

## P-15 兜底除法会把「双空响应」凑成 PATCHED

**总则**：判定路径上的**防御性写法本身就是判定逻辑**。
为避免除零而写的 `max(len_true, 1)`，把「分母为零」这个
**证据缺失**状态，悄悄改写成了「比例等于 0」这个
**证据充分**状态——判定语义被兜底改掉了，
而代码看起来更「健壮」了。

**机制**（`judge_t1` 修复前）：

| 步骤 | 表达式 | 双空响应下的值 |
|---|---|---|
| 差值 | `delta = len_true - len_false` | `0 - 0 = 0` |
| 比例 | `ratio = abs(delta) / max(len_true, 1)` | `0 / 1 = 0` |
| 逐字节一致？ | `sha_true == sha_false` | 同为 `e3b0c442…` → `True` |
| 落点 | `elif ratio == 0 and same_body:` | **PATCHED** |

`max(..., 1)` 让分母永不为零，于是「两边都没内容」
被算成了「两边完全一样」。

**为什么是 fail-open**：两个空响应**不构成任何证据**，
判据却读成了「已修复」。与 P-13 同向，区别在**根因层次**：
P-13 是**数据形状**问题（网关少给了一个键），
P-15 是**代码兜底**问题（判定器自己抹掉了分母为零）。
**P-13 的补丁修不了 P-15**：即使 `normalize_probe` 把每个
字段都补齐，`max(..., 1)` 依然会把两个空响应凑成 PATCHED。

**为什么一直没暴露**：三重遮蔽，缺一不可。

1. **靶场不产生这个形状**：真实靶场 len(1=1)=72B、len(1=2)=27B，
   `len_true` 从不等于 0；
2. **靶场侧行为兜住了**：R-T1-02 让「无注入标记的请求」返回 400，
   空响应体在到达判定前就被状态码检查拦下——但**那是靶场配合，
   不是判定器自身的防线**；
3. **测试只覆盖正常长度**：`max(..., 1)` 仅在 `len_true == 0` 时
   才让行为偏离正确值，而当时用例全是 `length=100/140/30`。

**泛化即打开**：换成空 body 的 200 响应目标（真实世界很常见：
被均衡器短路、被 WAF 静默吞掉），这条通道立刻打开，
且报出的结论是「已修复」。

**处置（已落地）**：

1. **拆掉兜底**：`ratio = round(abs(delta) / len_true, 4)`，分母不再兜底；
2. **显式前置守卫**：`len_true == 0` 直接返回 INCONCLUSIVE，
   rule_ref 指向新增的 `R-T1-04`（同步进 `rules.json` 并纳入必需键校验）；
3. **回归用例**：`test_t1_both_empty_body_inconclusive`（双空 → INCONCLUSIVE）、
   `test_t1_empty_true_body_inconclusive`（真空假非空 → INCONCLUSIVE）。

**判据的不对称是有原理的，不是双标**：分母是**真 payload 的基线长度**，
基线为空则比例无定义；而**假**探针为空、真探针非空时比例有定义
（`len_true / len_true = 1.0`），且正是布尔盲注的典型特征
（真 payload 取回记录、假 payload 取回空）。故只拦「真探针为空」，
由 `test_t1_empty_body_not_patched` 守住「假探针为空仍判 VULNERABLE」。

**第二层教训：断言写松，等于没测。** 本次修复中 `_inconclusive` 的
reason 因一个多余的逗号被截断（`"空响应不构成判定依据"` 被当作
独立实参传入后被 `isinstance(a, dict)` 过滤掉，静默丢弃），
而两条新用例只断言 `verdict` 与 `rule_refs`，消息拼坏与否一概不报。
补上 `assert "len_true=0" in out["metrics"]["reason"]` 后才会当场失败。
**证据链里每一个可读字段，都值得一条断言。**

**与 P-05、P-13 的关系**：P-05「探测失败 ≠ 修复成功」说的是
**外部**失败被误读为修复；P-13 说的是**数据形状**异常被补成正常值；
P-15 说的是**判定器自身的兜底**把异常形状抹平。三者同向——
**凡「让程序继续跑下去」的兜底，都要追问：它是不是顺手把结论也改了。**

## P-16 run_id 是 LLM 可控字符串，却能直通文件路径

**现象**：`call_octobus._append_call_log(run_id, ...)` 用 `EVIDENCE_DIR / run_id` 建目录，而 `run_id` 由调用方传入、无任何字符集校验。网关故障期间 Agent 为排查令牌，用 `tokchk-shell-env`、`rot-verify-BOGUS_控制组` 这类自选标识调用探针，于是 `evidence/` 下凭空长出一批目录 —— 其中 `rot-verify-BOGUS_控制组-110123` 的目录名含中文，是「非 ASCII 串真的变成了路径」的直接物证。

**为何危险**：`run_id` 一旦含 `..` 或 `/`，`EVIDENCE_DIR / run_id` 就不再困在 `evidence/` 内。这不是理论风险：决定这条字符串的是 LLM，而 LLM 的输入是漏洞记录与外部响应。同理，非 ASCII 进了 `x-octobus-ext-business-request-id` 头会在鉴权前抛 latin-1 编码错，把「编码失败」伪装成「鉴权失败」（与 R-4 同源）。

**对策**：`_check_run_id()` 限定 `^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$`，在**入口**（`call_method`，早于建请求头）与**落盘点**（`_append_call_log`，早于 `mkdir`）各拦一次；回归用例覆盖穿越、非 ASCII、超长与 `..`。首字符必须为字母数字，顺带挡住 `.` 与 `..` 及空串。曾由此产生的痕迹目录已清除。

**教训**：凡是「外部或模型可控的字符串 + 直接参与路径或协议字段」的组合，校验必须落在**字符串变成路径的那一行之前**，且不能只依赖调用方自觉。

## P-17 「配置已应用」不等于「运行态已更新」

**现象**：轮换令牌后执行 `ac up`，CLI 回显 project / agent / scheduler 三行 `updated`，看起来一切就绪；但此后连续三轮复测（`20261001030007-134`、`20261001040007-139`、`20261001050008-148`）探针全部 401，靶场侧一次都没被访问。同一时期 `ac config` 会把已解析的 `OCTOBUS_TOKEN_RETESTER` 明文回显到终端。

**为何危险**：两个方向都会把人带沟里。① 明文令牌顺手进了终端滚动缓冲、日志或截图；② 「CLI 说 updated」被当成「已经生效」，于是 401 被误读为网关侧故障，排查方向整体跑偏 —— 报错形态（401）与真实原因（旧令牌仍在使用）根本不在一条线上。

**对策**：凡涉及 `ac up` 的输出一律打码后再落屏；令牌轮换后**必须实测一轮**并检查 `octobus_calls.log` 全绿，才认定切换完成。本次三轮回溯轮次已作为对照样本入库（`evidence/20261001040007-139`、`20261001050008-148`），修复后一轮 `20261001070007-139` 全绿为证。

**教训**：配置项的判据是**实测通过**，不是 CLI 的回显文案。任何「改完就完事」的切换动作，都要配一条端到端的验证动作。

## P-18 声明里的数字没跟着证据走

**现象**：`rules.json` 与 `01_rules.md` 长期声明「17 轮采样一致，可复算」，而仓库内实际只有 4 个轮次（3 有效 + 1 错误）。从 `b97213b` 的 10 轮、到中期的 14 轮、再到 `2859746` 精简后的 4 轮，每一次证据集合变了，声明都没跟着改。

**为何危险**：这个声明是**可一条命令证伪**的 —— 当年那条裸命令一跑，得到的轮数就与声明的数字对不上（注：裸命令只罗列全部轮次，含 401 对照轮与空体轮，不构成本轮结论依据；带口径的复算见 `01_rules.md` R-T1-03）。一旦被验证，塌掉的不只是这个数字，而是**整份判据的可信度** —— 读者会合理地怀疑其它未经复算的声明。

**对策**：① 声明里的数字必须与仓库内可复算的证据对齐，并把**复算命令写进声明本身**，让读者能自行验证；② 定时复测每小时都会产生新轮次，手写数字注定持续腐烂 —— 因此用 `/evidence/2*/` 冻结自动收录，仓库只保留人工收录的快照（收录时显式 `git add -f`）。

**教训**：手写数字都会腐烂。要么让它可复算，要么让证据停止自动增长 —— 两者至少要占一样。

## P-19 「有证据」不等于「该入库」

**现象**：一批与本项目判定链毫无关系的痕迹目录（`rotchk-*`、`rot-*`、`b2https-*`、`b2revert-*`，共 11 个）随提交信息「令牌轮换的验证证据」被一并入库，其中 `rot-verify-BOGUS_控制组-110123` 的目录名含中文 —— 它本身就是 P-16 那个漏洞留下的物证。

**为何危险**：这些目录不被任何文档引用、也不参与任何复算，对读者只是噪声；更糟的是它们会被读成「交付物里混着调试残余」，直接削弱整份证据链的说服力。而提交信息声称它们是「验证证据」，等于把一个站不住的说法写进了历史。

**对策**：删除 11 个已跟踪 + 3 个未跟踪的痕迹目录，并把该事故记入本条；入库标准收紧为「**被 README / 规则文件 / 踩坑条目之一引用，且可复算**」，不满足就不入库。

**教训**：证据的价值不在数量，在**可被引用和可被复算**。留痕要有出口，没有出口的留痕就是垃圾。

## P-20 看起来合理的版本号，最难过审

**现象**：README 两处声明 `OctoBus v0.5.0`。三处交叉验证的结果是：镜像 tag 只有 `latest`（可变），CLI 自报 `version: main` / `commit 25badd7`，而镜像的 OCI 标签里**根本没有 octobus 的版本字段** —— 它是照抄基础镜像 Ubuntu 26.04 的标签。同一句基线里的 `agent-compose v2609.4.0` 反倒有据：`ac version` 自报与 daemon 镜像 tag 双向一致。

**为何危险**：`v0.5.0` 是「早期项目的典型版本号」，看着最合理 —— 所以它比任何离谱的错误都难过审。镜像 tag / CLI 自报 / OCI 标签三处只要不做，它就能一直待在那里；而读者一旦照着 README 敲 `docker run …:v0.5.0`，命令当场失败，整份部署文档的可信度一起陪葬。更隐蔽的是：就算 tag 存在，`latest` 也是会漂移的可变标签，唯有摘要能锁死。

**对策**：版本项必须三处交叉验证，命令写进正文备查 —— `docker images --format '{{.Repository}}:{{.Tag}}' | grep -i octobus`、`docker exec octobus octobus version`、`docker inspect octobus --format '{{json .Config.Labels}}'`。查不到语义化版本时，改用 **摘要 + commit** 锁定（`@sha256:…` 与 `commit 25badd7`），**绝不补一个看起来合理的版本号**。摘要只在仓库里写一次，其余位置引用它，避免同一个值多处漂移。

**教训**：审核要针对「合理性」，而不是「可疑性」。离谱的错误会自己暴露，合理的错误等你替它背书。

**同类第二例：Agent 自身的运行时镜像**。`agent-compose.yml` 把 guest 镜像钉在 `ghcr.io/chaitin/agent-compose-guest:latest`，实测该引用对应镜像构建于 2026-07-16、摘要 `sha256:a99584629d9f…`；而本机另有 11 天前构建的 `chaitin/agent-compose-guest:v2609.4.0`，两者摘要不同、**并非同一个镜像**。把运行时钉在可变标签上，意味着同一份交付在不同日子可能跑出不同行为 —— 已改为摘要引用。


## P-21 evidence 目录的属主并不总是本项目用户

**现象**：`evidence/` 下部分轮次目录属主是 `agentadmin`（10-01 11:00 及以前），部分是 `root`（12:00 起）。guest 容器确以 root 运行，有实测为证：镜像 `Config.User` 为空，`docker run --rm … id` 输出 `uid=0(root) gid=0(root)`。由 guest 写入的轮次必然以 root 落盘。

**未查明**：11:00 与 12:00 之间到底发生了什么导致写入者身份变化。逐条排除如下 —— ① guest 镜像未更换：daemon 日志中 `guest_image=` 出现 68 次且取值唯一；② `agent-compose.yml` 未改动：最近一次改动是 09-30 18:43；③ 无 agent 重启：10:30–12:30 日志仅有例行 session_start 与 cleanup，无配置应用事件；④ 不是「宿主机先建目录、guest 再写文件」：11:00 那一轮的目录内**文件**同样是 agentadmin 属主。四条皆不成立后停手，如实记为未查明。

**影响**：仅限本机 ops。属主不进 git（索引只记权限位、不记属主）、不影响判定结果、不影响交付内容；代价只是清理这些目录需要 sudo。

**对策**：文档化本现象，清理时用 `sudo rm -rf` / `sudo chown -R`；**不**把 guest 改成非 root 运行 —— 该镜像的内部初始化很可能依赖 root，为一个观感问题去冒「Agent 跑不起来」的风险不划算。

**教训**：排查的终点不总是根因，有时是「已排除清单」。把排除过程写清楚，比编一个顺口的因果更有价值 —— 前者可以被下一个人接着查，后者会把人引向不存在的地方。

## P-22 绝对断言最容易被一条命令证伪

**现象**：README 曾声明「Agent 与 OctoBus 容器在靶场日志的 `direct-or-other` 中**零出现**」。实测一条命令：

```bash
sudo awk -F'|' '/direct-or-other/ {print $2}' /var/log/vulnlab.log | sort | uniq -c
```

返回 8 笔——7 笔来自宿主机、**1 笔来自 guest 容器**（调试期在容器内手敲的连通性验证，`GET /`）。「零出现」当场崩塌。

**为何危险**：这份日志同时承载三类流量——复测业务（经网关）、人工运维（宿主机探活）、人工调试（容器内连通性验证）。把「业务链路干净」写成「日志里零出现」，等于用一个自己控制不了的集合，去支撑一个只需要业务子集成立的结论。**断言范围一旦超出可控制的范围，它随时可能被推翻。**

**对策（已落地）**：

1. **改相对断言**：README 第 7 节改为「判定链路的全部请求都经网关，与 `octobus_calls.log`、网关审计逐条对应，靶场侧无一落在 `direct-or-other`」——把断言范围收回到**业务链路**，而不是整份日志；
2. **判据放在业务侧**：判断有没有绕网关，看的是「每轮 7 次能力调用能否在 `octobus_calls.log` 与网关审计里逐条对上」，而不是「日志里有没有异物」；
3. 调试产生的直连**保留不清理**——检测机制只标记、不阻断，留痕本身就是它的价值。

**教训**：写声明前先问一句「这条断言覆盖的范围，我控不控制得住？」。**「零出现」「全部」「从不」这类绝对词，除非范围完全可控，否则就是给自己埋雷。**

## P-23 「WAF 没拦」不等于「漏洞还在」：v1 的 XSS 假阳性

**现象**：v1 的 `judge_t2` 写法是 `if not waf_active: VULNERABLE`。目标若已做真实修复（输出编码，返回 200 + `&lt;script&gt;`），字面量探针没有 403，`waf_active=False`，于是被判 VULNERABLE。代码注释写的是「字面量未被拦**且原样反射**」，实现却只检查了前半句。

**根因**：用一个信号（有没有拦截）代替了另一个信号（有没有反射）。反射检测还依赖 200 字符摘要里的硬编码标记（`onerror=alert(1)`），编码后的输出里这段文字同样存在，标记区分不了「原样」与「转义」。

**对策（v2 已实现，R-T2-01/02/03）**：
1. 探针新增 `search_terms` → `hits`，在**完整响应体**里计数；判定只认完整 HTML 破坏型 payload（含 `< >`）是否原样出现；
2. 每个探针归入 `blocked / reflected / escaped / absent / reflected_inert / unknown`，用状态矩阵判定，输出编码要求「编码串出现」这一正向证据；
3. 旧探针没有 `hits` 时降级为 `unknown`，**绝不据摘要里没看到就断言「未反射」**（三值逻辑 `common.term_state`）。

**教训**：注释里的「且」是需求，代码里没写出来就是缺陷。每个 `VULNERABLE` 分支都应该能回答「正向证据是什么」。

## P-24 「被拒绝」需要控制探针才有意义：水平越权的测法

**现象**：v1 的 T3 只对比「无 Cookie」与「`Cookie: admin=1`」，这测的是未授权访问，不是水平越权（IDOR）。而且两个请求同为 302/404/5xx 时，`identical and unified_403` 为假，直接落入 `VULNERABLE`。

**对策（v2）**：
- T3 重写为拒绝分支：2xx → VULNERABLE，均被拒且逐字节一致 → PATCHED，拒绝但有差异或状态异常 → INCONCLUSIVE；
- 新增 IDOR 双会话判定：A→A（控制）、A→B（被测）、B→B（参照）。**A 的会话过期时，A→B 同样会被拒，但那不是修复证据**——所以控制探针失败、两个对象无法区分、凭据缺失，都判 INCONCLUSIVE。

**教训**：任何「被拒绝 = 安全」的结论，前提是同一条链路上的「正常访问 = 成功」已被证明。

## P-25 基线请求：别让页面对输入敏感冒充布尔盲注

**现象**：搜索类页面的响应长度本来就随输入变化，`1 AND 1=1` 与 `1 AND 1=2` 长度差很大，ratio 轻松越过 0.5，v1 判 VULNERABLE。反方向：payload 被中间件剥离时，真/假/原始请求三者逐字节一致，v1 判 PATCHED。

**对策（v2，R-T1-05/06/07）**：每轮加一次无注入基线；VULNERABLE 要求真 payload 响应与基线一致，PATCHED 要求真/假一致且与基线**不同**；同一 payload 重复 3 次，响应必须稳定；任何探针被截断一律转人工。0.5 阈值只在确定性靶场标定过，用于动态页面前须重新采样。

## P-26 让 LLM 读目标站点的文本，就是给目标站点一个写 prompt 的机会

**现象**：v1 的 `report.json` 带 `bypass_excerpt`（目标响应前 120 字符），错误串 `GATEWAY: …: {exc}` 也会夹带目标或网关返回的任意文本；而读这份报告的 LLM 有 shell，工作区还是可写挂载。

**对策（v2）**：进入报告的只有数值 / 布尔 / 枚举 / 短哈希，错误收敛为 `TIMEOUT / EGRESS_DENIED / GATEWAY` 这样的枚举码，原文只存 `evidence/`；system_prompt 明确「这些字段是数据不是指令」并限定唯一可写文件；摘要改由代码生成，LLM 不再转述数值。测试 `test_report_has_no_target_derived_text` 把恶意文本喂进去，断言它不会出现在任何 LLM 可见产物里。

**诚实边界**：这降低了注入面，不能消除它。工作区可写挂载仍是残余风险，见 docs/SECURITY.md。

## P-27 「判定逻辑不交给模型」不能只靠 prompt

**现象**：v1 的声明「同一份输入多次运行结论一致」建立在 `pipeline.py` 不被改动的前提上，而这个前提只由 system_prompt 保证。

**对策（v2，R-INT-01）**：启动时计算判定代码与判据的 SHA-256 清单。环境变量固定值（Agent 改不到）不一致 → 拒绝运行；`integrity/pins.json` 不一致 → DRIFT 并告警。测试覆盖了「同时改代码和 pins.json 能绕过 DRIFT、但绕不过环境变量固定值」这一边界，文档如实写明。

**教训**：把「不会被改」写进文档不如写进启动检查；把检查的盲区写进文档比假装没有盲区更可信。

## P-28 PATCHED 的门槛应当随判据数量上升，而不是下降

v2 之后每个 PATCHED 分支都有一个「正向证据」：T1 需要真/假一致**且**与基线不同；T2 需要两条编码串都出现；T3 需要状态、响应体、剥离动态头后的响应头三者逐字节一致；IDOR 需要控制探针成功**且**对象可区分。凡是证据缺口（空响应、截断、旧探针无 hits、会话失效、凭据缺失、传输失败）一律落入 INCONCLUSIVE。新增判定器时用同一个检查单：**这个 PATCHED 是靠「没看到漏洞」得出的，还是靠「看到了修复」得出的？**
