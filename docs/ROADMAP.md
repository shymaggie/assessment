# 改进计划：个人 PC 业务安全可视化工作台

> 更新日期：2026-10-14
> 状态：设计与实施计划，**本文件不代表 Web 界面、新增检查或个人 PC 安装包已经实现**。
> 基础：当前本地 `agent-assessment` 的确定性复测管线、四类判定器、OctoBus 探针与证据链。
> 本轮交付：产品范围、页面方案、技术架构、PC/腾讯云部署方案、分期任务和验收标准；不修改现有运行代码。

## 1. 产品定位与核心决策

将系统从“需要编辑 JSON 和运行命令的漏洞复测脚本”升级为**业务安全验证工作台**。

普通用户用浏览器完成：新建业务 → 添加已授权目标 → 选择检查模板 → 预检并确认 → 启动任务 → 查看问题与证据 → 导出整改计划。

五项决策：

1. **个人 PC 优先**：本地页面、本地任务、本地数据；日常操作不需要终端，不强制安装 Docker 或购买云服务器。
2. **保留现有引擎**：Web 层管理业务和任务，不把安全判定交给 LLM，不重写已验证的算法。
3. **两条执行路径**：新增受控本地执行器用于 PC；保留 OctoBus 作为可选网关执行器。两者必须有明确能力标识和一致性验收。
4. **先做真实闭环，再加安全模块**：先让已有四类复测能在页面操作，再逐步加入低影响检查、授权控制验证和业务流程验证。
5. **安全边界不是菜单功能**：有授权范围才能执行；目标响应不直接作为 HTML 显示；演示数据与真实结果严格分开。

不定位为通用扫描器、终端杀毒软件、摄像头/视频安防平台，也不保证发现所有漏洞。提供的是**对指定业务安全控制的可重复验证与证据管理**。

## 2. 用户与典型场景

| 用户 | 主要需求 | 默认操作方式 |
|---|---|---|
| 个人开发者、网站维护者 | 上线前检查自有网站配置、验证历史漏洞修复 | PC 本地模式，模板向导 |
| 小团队业务负责人 | 看哪些问题未整改、复测是否通过、谁负责处理 | 总览、整改看板、报告 |
| 开发与测试人员 | API 权限回归、版本间差异、安全配置验收 | 测试环境任务、历史对比 |
| 安全与运维人员 | 凭据与授权范围管理、证据复核、持续复测 | 专业模式、审计、服务器部署 |

### 2.1 普通用户首次使用流程

1. 打开桌面启动器，自动启动本地服务并打开浏览器。
2. 选择“查看演示”或“检查我的业务”。演示页面始终标明“本地演示，不代表真实业务结果”。
3. 新建业务，填写名称、环境（开发/测试/生产）、负责人。
4. 登记目标域名和接口，确认授权、有效期、允许路径、请求预算；未授权目标不能运行。
5. 默认推荐低影响配置检查；历史漏洞复测需要填写已知漏洞和对应模板。
6. 点击“预检”：显示网络可达性、凭据状态、请求数量、预计最长耗时和可能影响。
7. 点击“开始检查”，看到排队、执行进度、失败原因，而不是一直等待空白页面。
8. 查看“问题 → 证据 → 修复建议 → 再次验证”，导出 Markdown 整改报告。

凭据管理和高影响操作位于专业模式；新手引导不要求用户理解 `capset`、`protojson` 或编辑 `rules.json`。

## 3. 当前基础与真实差距

### 3.1 已有能力，优先复用

| 能力 | 现有文件 | Web 化用途 |
|---|---|---|
| 管线入口及运行上下文 | `src/pipeline.py`、`src/common.py` | 创建任务、执行、关联运行记录 |
| 布尔盲注、反射 XSS、伪造凭据越权、IDOR | `src/judges.py`、`src/probes.py`、`data/vulns.json` | 首批可视化检查模板 |
| 五态结论与原因码 | `src/common.py`、`src/judges.py` | 状态标签、人工复核解释 |
| 状态变化、告警队列、确定性摘要 | `src/state.py` | 回归提醒、趋势、报告基础 |
| 证据、留存和代码清单 | `src/evidence.py`、`src/integrity.py` | 证据查看、完整性提示 |
| 受控 HTTP 探针 | `services/retest-probe/bin/probe-lib.js` | OctoBus 模式的执行护栏参考 |
| 本地靶场、假网关、契约与属性测试 | `vulnlab/`、`tests/` | 引导与回归测试，不作为生产网关 |
| 报告契约 | `docs/report.schema.json` | 报告导入及结构校验的起点 |

目前**没有**管理型 Web API、前端工程、业务数据库、PC 启动器；Node 文件是探针，不是浏览器页面。`Dockerfile` 也不是包含 Web 系统的完整应用镜像。

### 3.2 Web 化前必须解决的集成问题

| 问题 | 当前行为 | 计划 |
|---|---|---|
| 网关配置不是任务级注入 | `run(env=...)` 并不注入网关地址/令牌；客户端仍读取 `os.environ` | 引入不可变客户端配置与执行器接口，禁止在 Web 线程间切换全局环境变量 |
| 证据和调用日志可能分开 | 探针文件使用 `ctx.evidence_dir`，调用日志使用模块全局 `EVIDENCE_DIR` | 两者都从任务上下文取路径；增加目录一致性回归测试 |
| 全局可变状态仍在 | Run ID 计数器、默认上下文、插件表、数据目录和限速器 | 过渡期独立 worker 子进程 + 全局串行；后续 UUID 任务 ID、固定插件注册表、显式上下文 |
| 文件写入非原子 | 报告、历史和上一轮状态直接覆盖 | 完整任务快照 + SQLite 事务发布；运行中页面读取进度，不读半写入报告 |
| 没有业务隔离 | 状态仅按 `vuln_id` 比较 | 按 `(business_id, check_id)` 保存基线；不同业务使用独立凭据、目录和执行器配置 |
| 在线规则与 pin 冲突 | 完整性清单绑定仓库规则和漏洞文件，直接编辑会漂移 | 内置代码固定；业务配置草稿、校验、发布、回滚，单独记录实际执行配置摘要 |
| 规则语义校验不足 | 当前主要验证必需键 | 类型、范围、组合和安全不变量校验；传输失败必须为 `INCONCLUSIVE`，不能在线改成通过 |
| 完整性边界不完整 | 主要检查磁盘文件，不完整覆盖实际内存配置、Node 探针和依赖 | 报告绑定代码、插件、配置、执行器版本；可信发布校验器，不把“重新 pin”当自动批准 |
| PC 网络默认值不适配 | 默认使用 `172.17.0.1`，部署依赖 bash/systemd | PC 采用回环地址和动态端口；云网关地址显式配置，不假设 docker0 地址 |
| 自动留存缺少活跃任务概念 | 按目录名和标记清理 | 清理只针对已完成、非锁定任务；改 UUID 后同步迁移旧目录识别逻辑 |

第一阶段不能把 `pipeline.run()` 简单放进 HTTP 请求线程后就宣称支持并发。

## 4. Web 页面与交互设计

导航建议：**总览 / 业务与目标 / 检查中心 / 任务中心 / 问题与整改 / 证据与审计 / 报告 / 系统设置**。

| 页面 | 核心内容 | 必须可操作 |
|---|---|---|
| 总览 | 当前业务、未处理问题、任务状态、覆盖率、最近回归、连接健康 | 切换业务、查看异常、创建任务 |
| 业务与目标 | 业务/环境树、域名和接口、负责人、授权范围与到期时间 | 新建/归档业务、登记目标、授权确认、连通性预检 |
| 检查中心 | 模板库、适用条件、影响等级、所需凭据、执行器支持情况 | 选模板、填参数、预估请求、保存检查集 |
| 任务中心 | 排队/执行/取消/中断状态、逐步骤进度、脱敏日志 | 启停任务、重新运行、定时设置、查看详情 |
| 问题与整改 | 严重度、证据置信度、负责人、截止时间、版本变化 | 指派、评论、提交修复说明、触发复测、审核关闭 |
| 证据与审计 | 请求与响应度量、哈希、规则版本、调用链、操作记录 | 安全预览、对比、脱敏导出、保留/解除保留 |
| 报告中心 | 历史运行、检查覆盖、未结问题、Markdown 整改计划 | 生成、下载、对比、按业务和版本筛选 |
| 系统设置 | 本地/网关模式、凭据引用、通知、主题、数据目录、备份 | 测试连接、设置请求预算、导出脱敏配置 |

### 4.1 单个问题详情

采用“左侧问题与证据、右侧整改状态”的布局，回答：

- 检查了哪个已授权目标、哪个版本？
- 为什么判定为失败、已修复或需要人工复核？
- 哪些证据能直接复核，哪些只是有限样本？
- 建议由谁在何时修改什么，如何验证完成？

`INCONCLUSIVE` 必须独立显示，不得归入安全；`WAF_FULL_BLOCK` 必须说明“有限样本被拦截，不等于代码层修复”。

### 4.2 视觉与可用性

- 采用 Linear/Modern 的克制工具型布局，默认浅色、可选深色；不用装饰性霓虹、自动漂浮动画或满屏渐变。
- 单一靛蓝交互强调色；风险状态使用语义色，**同时配文字与图标**，不只靠颜色区分。
- 系统字体优先，资源本地打包；不依赖 Google Fonts、CDN 或外网图片，适配个人 PC 和大陆云环境。
- 数据表支持筛选、分页、保存视图；空状态给出下一步，失败状态有明确原因和恢复路径。
- PC 主场景覆盖 1280×720、1440×900、1920×1080；窄屏支持看报告和停止任务，不强迫手机填写复杂专业模板。
- 完整键盘操作、可见焦点、表单错误定位、图表文字摘要；目标响应按纯文本显示，禁用不可信 `v-html`。

## 5. 业务安全功能矩阵与扩展顺序

**菜单、检查实现和安全证明是三件不同的事。** 下表均需有实现、测试数据与明确判据，才能从“规划”变为“可用”。

| 能力 | 内容及可视化 | 通过/结论的证据要求 | 阶段 |
|---|---|---|---|
| 历史漏洞复测 | 当前四类复测，真假请求、反射/编码、双会话对象对比 | 沿用现有确定性判据，保留适用范围与人工复核 | P1，已有核心 |
| HTTPS 与证书 | 指定域名的证书链、有效期、主机名匹配、HTTP 跳转 | 完成实际 TLS 验证；超时是未知，不是正常 | P2 |
| 安全响应头 | CSP、HSTS、点击劫持防护、内容类型策略 | 按所选应用场景核验配置；CSP 存在不等于 XSS 已修复 | P2 |
| Cookie 与会话配置 | Secure、HttpOnly、SameSite、会话轮换观测 | Cookie 可观测且策略适用；不能仅凭属性推断会话业务逻辑安全 | P2 |
| CORS 配置 | 已授权 Origin 请求矩阵、凭据允许行为 | 检查 Origin、响应头和浏览器语义；头信息只是控制验证，不直接等于数据泄漏 | P2 |
| API 与对象级权限 | 账号角色×接口矩阵、自己的对象/他人的对象 | 合法正向控制成功、对象可区分、跨角色或跨用户结果可复核 | P2，复用 IDOR |
| 输入校验与错误脱敏 | 指定接口的小规模无害边界输入、错误信息泄露 | 对照 API 契约；“未回显”不能代替参数化或业务校验证明 | P2 |
| 账号会话生命周期 | 注销后失效、过期、轮换、测试账号隔离 | 正常会话对照成功、注销/过期后对应受保护请求被拒；需要测试环境账号 | P3 |
| 限流与防重复提交 | 固定小预算内的响应、幂等键与重试行为 | 对照约定窗口和业务状态；不压测、不遍历凭据、不批量发验证码 | P3，仅测试环境 |
| 订单、支付、优惠与审批 | 状态流转图、合法流与禁止流、幂等回执 | 用户提供测试契约、沙箱账户和可恢复数据；需服务端状态证据，不能靠响应长度判定 | P3，仅沙箱、默认关闭 |
| 敏感信息暴露 | 已授权页面/响应中的疑似密钥、错误堆栈、过量字段 | 规则候选 + 脱敏展示 + 人工确认，误报可复核；不尝试使用发现的密钥 | P2/P3 |
| 依赖与组件风险 | 用户提供的锁文件/SBOM/审计报告，版本及整改分组 | 标明数据来源和更新时间；本地库过期或断网时显示未知 | P3，优先导入 |
| 腾讯云配置复核 | 只读导入配置或官方审计结果，网络暴露、证书、访问控制差异 | 与目标策略比对；导入检查不等于实时云扫描 | P3，可选 |
| 整改与持续验证 | 问题指派、修复说明、复测证据、到期提醒 | 新一轮通过证据 + 审核，不能只点按钮修改机器判定 | P1/P2 |

### 5.1 风险分级与执行预算

- **低影响检查**：已登记路径的少量请求与配置读取，不称“纯被动”；即便 GET 也可能产生服务端副作用。
- **主动复测**：现有注入/权限类模板，要求明确授权、请求预算、测试账户和确认。
- **状态改变检查**：注销、订单状态、审批、幂等验证仅在测试/沙箱环境按计划执行，默认关闭。
- 禁止默认端口扫描、目录枚举、凭据猜测、真实资金交易、批量注册、批量短信/邮件或自动扩展目标范围。
- 不提供在线 Python/JS 插件上传执行；插件只能经可信开发发布流程安装。

## 6. 个人 PC 与腾讯云的三种运行模式

| 模式 | 用途 | 依赖及边界 |
|---|---|---|
| 演示模式 | 普通用户体验页面与整改闭环 | 本机回环靶场；固定测试数据；不访问外部业务；明确演示标识 |
| 本地授权模式 | 在个人 PC 检查自己的业务或已授权测试环境 | 本地 Web API + worker + 受控本地执行器；无需 Docker、Node 和 LLM 作为终端用户运行前提 |
| 网关/服务器模式 | 团队共享、长期任务、腾讯云部署 | OctoBus 执行器 + Linux 服务；LLM 解读可选，agent-compose 不强制成为 Web 控制层 |

### 6.1 PC 支持计划

| 平台 | 交付方式 | 要求 |
|---|---|---|
| macOS Apple Silicon / Intel | 初期统一 Python 启动命令；后续签名/公证启动包 | 分别验证 arm64、x86_64；不假定锁定的云镜像支持双架构 |
| Windows 11 x64 | PowerShell 开发入口；后续签名安装包或启动器 | 无 systemd、无 `/dev/null` 假设；进程停止与路径单独测试 |
| Linux x86_64 | 同一 Python 入口、可选用户服务 | 不强制 root；服务器模式再启用 systemd |

计划提供 `start-local`、`start-demo`、`doctor`、`stop` 等统一入口，由 Python 实现跨平台生命周期。正式安装包内携带前端构建产物，用户不必运行 Vite；安装包的 Python 运行时建议固定到受维护版本，原有 CLI 的 Python 3.10 兼容性另行保留。

**浏览器能打开不等于已跨平台支持**：启动器、OS 密钥库、网络、路径、进程取消、打包资源、睡眠唤醒都必须实测后才能写“已支持”。

### 6.2 PC 定时任务的真实边界

- 用户关闭程序、电脑关机或休眠时无法持续检查，页面要显示“调度已停止/错过的执行”。
- 恢复后按策略最多补一次，不集中补发所有历史任务，不对目标突发请求。
- 应用打开期间使用单一调度器；后台常驻再提供 macOS LaunchAgent / Windows 用户计划任务。
- 需要 24 小时检查的用户应部署到 Linux/腾讯云，不以 PC 睡眠状态承诺持续防护。

### 6.3 腾讯云部署

适用腾讯云 CVM 的 Linux 环境，不依赖某家云厂商的专有运行接口：

- 第一阶段建议 Ubuntu 24.04 LTS / Python 3.12 + 同一 Web 服务；已有 Ubuntu 22.04 路径保留兼容，但不直接复用写死路径/用户的旧部署脚本。
- 团队使用通过 HTTPS 反向代理或 VPN；禁止把本地模式配置直接改成 `0.0.0.0` 暴露公网。
- CVM 安全组、主机防火墙、应用认证共同限制访问；内部 API、SQLite 和执行 worker 不开放公网端口。
- 公网业务与 VPC 内网业务分别登记目标及网络策略；网关允许范围与页面登记范围必须一致。
- 若 `ghcr.io` 拉取困难，支持经授权的镜像中转到 TCR，并保存原镜像摘要、架构与导入记录，不用未核验的镜像替换。
- 本地执行器可无需 Docker 工作；若使用 OctoBus，则需要真实镜像、SDK、capset 和只读挂载验收。
- 不默认连接腾讯云账号。后续官方 API 集成只授予所需只读 CAM 权限；更高权限操作不在本计划内。

## 7. 推荐技术架构

### 7.1 技术选型

| 层 | 推荐 | 理由与边界 |
|---|---|---|
| Web API | FastAPI + Uvicorn + Pydantic | 有明确接口契约、表单校验、OpenAPI；作为可选 `web` 依赖组，不把第三方依赖装入原引擎 |
| 前端 | Vue 3 + TypeScript + Vite + Vue Router + Pinia | 适合管理控制台；独立工程，正式发行预构建；Node 仅是开发/构建依赖 |
| 组件及图表 | Naive UI + ECharts，按需使用 | 完整表单、数据表和语义状态；图表有文本替代，不展示虚构指标 |
| 持久化 | SQLite WAL + 版本化迁移 | 个人 PC 单机成本低；新增 Web、多业务和查询需求后，采用 DB 的理由与原 CLI 不同 |
| 证据存储 | 每业务/任务目录 + SQLite 索引 | 原始证据不全部塞入 DB；索引保存大小、哈希、脱敏版本和保留状态 |
| 任务 | 数据库队列 + 独立 worker 子进程 | 初期全局串行；避免全局 env 串业务；不立即引入 Redis/Celery |
| 进度 | SSE + 可恢复事件游标 | 适合单向状态推送；最终结果由持久化 API 获取，SSE 断线不丢任务 |
| 凭据 | OS 密钥库，服务器端加密库 | Windows/macOS/Linux 按实际可用后端验证；加密主密钥不与 DB 放在一起；密钥库不可用时不静默明文降级 |
| 分发 | 先统一 Python 启动器，后独立桌面启动包 | 不先上 Electron/Tauri；无需同时承担 Rust/桌面运行时与浏览器产品两套维护 |

具体版本在实施时锁定到 `uv.lock`、前端锁文件及测试矩阵，不在规划文档中臆造“最新版本”。

### 7.2 数据流

本地浏览器 → Web API（认证、授权、模板校验）→ SQLite 任务队列 → worker → 执行器 → 已授权目标。

worker → 不可变运行快照/证据 → DB 事务发布任务结果 → SSE/页面 → 整改与报告。

LLM 只允许读取脱敏、结构化的结果视图并生成可选说明；不持有业务会话，不接收原始 HTML，不改动机器结论。无 LLM 时所有主要功能可用。

### 7.3 引擎适配：两条路径而不是绕过护栏

引入 `Executor` 接口，显式提供 `probe_http`、算术度量、审计输出、能力清单和取消信号：

- `OctoBusExecutor`：注入网关地址、token 引用、capset、探针/计算实例及任务上下文；保留实际网关审计。
- `LocalExecutor`：使用受控本地 HTTP 传输和本地确定性算术，所有步骤写本地审计。必须实现 URL/端口/路径范围、DNS 实际连接地址校验、TLS 主机名验证、跨目标凭据禁止、超时、解压后响应上限、请求预算、重定向策略。
- 演示执行器只访问本机测试靶场；不能直接把 `tests/FakeGateway` 包装成生产安全网关。
- 云元数据、链路本地、组播等禁止目标有硬限制；用户自己的回环或私网服务需按显式授权策略允许，不是一刀切禁止所有内网。
- 生产缺少执行器能力时返回 `UNSUPPORTED/INCONCLUSIVE`，不从网关故障自动降级为直连。
- 报告区分 `audit_source=local/octobus/demo`，本地审计不冒充第三方网关证据。
- 本地连接必须将“已校验的 DNS 结果”用于实际连接并保持正确 TLS SNI/证书验证；不得为减少实现难度关闭证书验证。

### 7.4 任务、业务隔离与发布

过渡方案：每业务固定工作数据目录，同业务不重叠运行，全局单 worker；独立子进程启动前设置专属环境，`.env` 禁止覆盖任务已注入的配置。保留上一轮状态，不能每轮空目录导致历史比较丢失。

正式方案：不可变 `JobConfig` + `RunContext` + 显式客户端；报告完成后保存到任务独立目录，经结构和证据校验后在 SQLite 事务中发布，才更新该业务“最新运行”指针。

任务状态：`QUEUED → RUNNING → SUCCEEDED / FAILED / CANCELLED / INTERRUPTED / BLOCKED`；报告里的漏洞结论与任务状态分开，成功执行也可能全部为 `INCONCLUSIVE`。

进程故障后以租约/心跳识别中断任务，不把未知执行当成功。取消只能停止本机 worker 后续动作，**不能保证撤回目标已收到的请求**。每任务独立进程/进程组，不按名称杀死其他 Python 程序。

## 8. 数据模型与 API 范围

建议表：`businesses`、`targets`、`authorizations`、`credential_refs`、`check_definitions`、`rule_versions`、`jobs`、`job_events`、`runs`、`check_results`、`findings`、`finding_events`、`evidence_index`、`schedules`、`notification_outbox`、`audit_events`。

关键约束：

- 所有业务对象带 `business_id`，服务端验证归属；不能只靠前端隐藏。
- `(business_id, run_id)` 唯一；状态比较使用业务、环境、检查配置和基线版本，不跨环境比较。
- 运行绑定规则发布版本、执行器版本、目标清单摘要及凭据引用；实际执行配置独立摘要入报告。
- 机器 `verdict` 与人工整改 `status` 分列；人工关闭不能改机器结果，接受风险须记录理由和期限。
- 数据迁移有 schema 版本、备份和回滚说明；SQLite 数据目录排除同步盘/网络盘作为默认存储。

计划 API（不是目前已有接口）：

| API 组 | 责任 |
|---|---|
| `/api/session`、`/api/health`、`/api/capabilities` | 登录、连接状态、演示/执行器能力 |
| `/api/businesses`、`/api/targets`、`/api/authorizations` | 业务、目标、范围与授权 |
| `/api/credentials` | 只处理引用、验证和删除，不提供明文“列表”接口 |
| `/api/templates`、`/api/check-sets`、`/api/rule-versions` | 模板、检查集与发布版本 |
| `/api/jobs`、`/api/jobs/{id}/cancel`、`/api/jobs/{id}/events` | 提交任务、取消、SSE |
| `/api/runs`、`/api/findings`、`/api/evidence` | 结果、整改流转、受限证据读取 |
| `/api/reports`、`/api/schedules`、`/api/notifications` | 导出、计划任务、通知策略 |

写接口支持幂等键、权限和审计；列表分页；证据按 ID 读取，不接受浏览器传任意磁盘路径；导出接口有大小和数量限制。

## 9. Web 化新增的安全要求

1. **本机默认只监听 `127.0.0.1`**，不等于不需要认证：恶意网页也可能向本机发请求。采用服务端会话/首次配对、严格 Host 与 Origin 校验、写操作 CSRF 防护；CORS 不使用通配符。
2. Cookie 使用 HttpOnly、适合本地场景的 SameSite；HTTPS 下启用 Secure。首次配对凭据不放查询串、不记录到日志，短期单次使用；桌面启动器不是免认证后门。
3. **证据安全显示**：HTML、URL、响应头、错误、Markdown 全部视为不可信；纯文本预览、禁用原始 HTML Markdown、CSP 与附件下载策略，避免存储型 XSS。
4. **敏感信息保护**：请求头名称隐藏并不足够；URL 查询、响应体、Set-Cookie 也可能含会话/个人信息。按角色、字段和模式脱敏，原件访问审计，备份默认不含可复用密钥。
5. **范围和 SSRF**：目标、网关地址和通知地址分别校验，拒绝非 HTTP 协议和 URL userinfo，限制重定向和 DNS 重绑定；不能把“localhost 运行”当成任意内网访问许可。
6. **模板不是远程代码执行入口**：Web 只编辑声明式参数和已发布规则；不接受 shell 命令、自由 Python、任意插件导入路径。
7. **配置不能破坏 fail-closed**：传输失败、取消、证据不足保持未知；浏览器不能修改安全不变量。发布规则需检验阈值、字段类型和正向控制条件。
8. **代码与配置完整性分开**：开发更新可评审后更新 pin；用户编辑业务配置不改源码、不自动为未知代码重新 pin。实际配置摘要、版本与执行结果关联。
9. **报表不是模型评分话术**：展示检查覆盖、证据和限制，不写“系统绝对安全”或强制给满分；任何安全分数都必须能展开计算依据。

## 10. 整改报告与评分展示

首期输出可编辑 Markdown，不新增 Office/PDF 工具链。报告包括：

- 业务、环境、目标授权范围、执行时间和版本。
- 已执行、未执行、不支持和未知的检查数量。
- 风险清单：证据编号、影响、置信度、受限条件。
- 整改计划：建议动作、负责人、优先级、预计工作量区间、截止时间、验收步骤。
- 原有漏洞五态与新增控制验证结果，单独展示人工整改状态。
- 代码/配置/执行器/证据摘要、上一轮对比及导出脱敏说明。

不要强行把证书检查的“通过”命名为 `PATCHED`。新增通用状态采用 `PASS / FAIL / INCONCLUSIVE / NOT_APPLICABLE / UNSUPPORTED`；保留原始漏洞五态，通过 UI 映射统一展示。

可选“已验证控制通过率”只在有足够样本时显示：已适用且完成确定判定的控制中，通过项占比。必须同时展示覆盖率、未知项和严重问题；没有检查到的项目不能加分，重大失败不能被平均分隐藏。该指标不是整套业务安全证明。

机器事实、模板整改建议、用户填写内容和可选 LLM 解读分开标识；本地无 LLM 时也能生成完整整改计划。

## 12. 本轮结论与下一步

优先实现 **P0 + P1**：把已有四类复测变为个人 PC 可操作、可理解、可复核的 Web 产品。这比先堆几十个安全菜单更有价值。

首次开发仍需要确认：首发平台顺序、是否允许主动模板连接真实业务、业务数量与并发需求。默认建议 **macOS 优先、Windows 紧随、单用户本地模式、全局单 worker、演示与真实授权检查分开**；团队共享与腾讯云长期运行随后实施。

本计划不会改变原项目的信任原则：**确定性代码负责判定，证据不足转人工；Web 负责把这一流程变得可用，而不是把未知结果包装成安全。**
